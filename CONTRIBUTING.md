# Contributing

Short version: spec first, tests written blind, then code.

## Process

1. **Spec first.** Behaviour is defined in `specs/` (shared rules in `specs/00-conventions.md`, one file per plugin). A change that alters behaviour starts with a spec edit, including a numbered "behaviour contract" statement for anything observable (text, toasts, denies, state values). Keep specs precise enough that someone who has not seen the code could test them. The spec is the oracle.
2. **Code-blind tests.** Contract tests are written from the spec only by someone (or some agent) who has not read the implementation, and the implementer does not read the tests. This stops code and tests from being fitted to each other. The process, roles and rules are in [`docs/code-blind-tdd.md`](docs/code-blind-tdd.md). The contract tests live in a separate **private** repository, so outside contributors cannot run them (see below). If you change observable behaviour, say which spec statements change; a maintainer will have tests updated or added blind.
3. **Implement.** Plugins live in `plugins/<name>/`. Rules that matter when editing:
   - Code used by two or more plugins lives in `shared/` and is copied into `plugins/*/hooks/_shared/` by `node scripts/sync-shared.ts`. Edit `shared/`, never the generated copies. `node scripts/sync-shared.ts --check` fails on drift.
   - A plugin cannot import another plugin. Cross-plugin reads go through published state atoms (see conventions section 2).
   - `claude plugin validate` follows `$` only inside `hooks/register.tsx`; keep every `$` call there and pass pure helpers a facade (conventions section 12).
   - `userConfig` keys cannot contain dots: write `mod_git_enabled`, not `mod.git.enabled`.
   - Plugins spend no tokens; a hook must never call a model API unless its spec says so.
4. **Docs.** Update the plugin README (options table follows `plugin.json`), the spec, and the version in both `plugin.json` and `.claude-plugin/marketplace.json`.

## Checks you can run

Requirements: Claude Code, Node (runs `.ts` natively by type stripping), and TypeScript via `npx`.

```
node scripts/sync-shared.ts --check
claude plugin validate plugins/<name>
npx --yes -p typescript@5.6 tsc -p plugins/<name>
npx --yes -p typescript@5.6 tsc -p shared/tsconfig.json
```

`tsc` needs the Claude Code plugin API typings at `.dev/plugin-authoring/types/claude-code.d.ts` (path relative to the repo root; each plugin's `tsconfig.json` includes it). The `.dev/` folder is git-ignored. The file is not generated by this repo: it comes from the `plugin-authoring` skill bundled with Claude Code, whose `types/claude-code.d.ts` is regenerated for each Claude Code build. Copy it from your installed build's copy of that skill:

```
mkdir -p .dev/plugin-authoring/types
cp <path to the bundled plugin-authoring skill>/types/claude-code.d.ts .dev/plugin-authoring/types/
```

## Running the contract tests (maintainers)

```
export BENTO_TESTS_DIR=/path/to/the/private/tests/repo   # folder with one subfolder per plugin
scripts/run-contract.sh <plugin>                        # safety | usage | awareness | agents | dev | compact
```

The script copies `plugins/<plugin>` to a temporary directory, copies the whole `$BENTO_TESTS_DIR/<plugin>/` folder (helpers included, `CONTRACT-MAP.md` excluded) into `contract/`, runs `claude plugin test` on it and prints only pass/fail counts and the names of failing tests. It never prints test source and exits non-zero on any failure or runner error. Without `BENTO_TESTS_DIR` it looks in `$HOME/CodeBase/bento-mods-tests`, which only exists on the maintainer's machine.

For the token-budget tool the same applies: its tests are in the private repo, and it can be exercised by hand against fixtures using the environment overrides listed in `tools/token-budget/README.md`.

## Gate for a plugin change

`claude plugin validate` clean; `tsc` clean (two pre-existing errors in `plugins/dev` are known, see its README); contract tests green (maintainers); the spec's manual acceptance list for anything the mocks cannot show (real `git`, `gh`, `lsof`, the desktop app).

## Privacy of contributions

No personal data, paths under a real home directory, email addresses, session ids or cost figures from your own sessions in code, tests, specs or docs. Use `$HOME` or `~`. `setup/secret-scan.sh` runs a regex scan (and `gitleaks` if installed); see `.secret-scan-allow` for the few allowed placeholders.

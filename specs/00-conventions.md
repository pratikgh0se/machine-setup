## 1. Repo layout and packaging
1. One plugin = one folder `plugins/<name>/` with `.claude-plugin/plugin.json`, `hooks/hooks.json` (`{"modules":["./register.tsx"]}`), `hooks/register.tsx`, `hooks/mods/<mod>.tsx`, `hooks/_shared/` (generated), `types/index.d.ts`, `README.md`. Only one module per plugin is allowed (R:12), so `register.tsx` imports the mods.
2. A mod file exports `const mod: Mod = { id, register(on, ctx), segments?(ctx), pane?, commands? }`. `register.tsx` calls `mod.register` for each mod whose `options['mod.<id>.enabled']` is not false. A disabled mod registers no hooks and draws nothing.
3. Plugins cannot import each other (only files of the plugin load, R:14). Code used by 2+ plugins lives in `shared/` at the repo root and is copied to `plugins/*/hooks/_shared/` by `scripts/sync-shared.ts` (`--check` fails CI on drift). Copies carry a "GENERATED, edit shared/" header. Shared files: `tokens.ts` (CSS block from `06-still-room-digest.md`), `svgkit.ts` (bevel, segment meter, chip, text fit), `glyphs.ts` (section 6), `band.tsx` (section 4), `toast.ts` (section 7), `proc.ts` (section 8), `pace.ts`, `cache.ts`, `prices.ts`, `testparse.ts`, `snapshot.ts`, `peers.d.ts` (typed slices of the other plugins' public atoms, section 7.5), `mascots.ts` (base64 of the two PNGs, generated by `scripts/gen-mascots.ts`), `fmt.ts`.
4. Marketplace `.claude-plugin/marketplace.json` lists all five plugins, `category: "mod"`. Install: `/plugin install <name> --marketplace pratikgh0se/machine-setup` (R:87). Versions start at `1.0.0`; `agents` replaces `agent-pets` (see agents.md section 0).
5. `plugin.json` fields: `name`, `version`, `description`, `types: "./types/index.d.ts"`, `author`, `userConfig` (shape as savvy-progress `plugin.json`: `type`, `title`, `description`, `default`, optional `options`). Options arrive as `register(on, options)` (T:7648). Booleans/numbers/strings only; every threshold in a spec is a `userConfig` field named in its "Options" list.
6. Commands: register in `session.start`, serve with `command.run{command}` (T:3091). A built-in name is refused, so at start call `$.command.list()` (T:3064) and, on collision, register `<plugin>-<name>`. No command may be named `usage`, `diff`, `status`, `config`. `$.command.list()` is not a complete oracle: a built-in alias (for example `/review`, an alias of `/code-review`) is refused by `$.command.register` yet absent from the list. Rule: attempt the bare name; if the host refuses it, or the list shows a collision, register `<plugin>-<name>`. A refusal is never silently dropped before the fallback runs. A fake host in tests must refuse built-in names and may omit aliases from `command.list`. A command that cannot be registered under either name is omitted without affecting the plugin's other commands.

## 2. State
1. Anything a render reads lives in `$.state` atoms declared in `types/index.d.ts` `PluginState['<plugin>']` (R:118, T:3384). Atom refs use string literals `{ plugin, key }`. Render hooks never write.
2. Cross-session values go to `$.store` (T:3351), JSON, 4 MiB cap, keys `<mod>:<name>[:<id>]`, every value `{ v: 1, ... }`. Two sessions may write concurrently and atomicity is UNVERIFIED: store per-session keys, merge on read, never read-modify-write a shared counter.
3. Module variables are caches only (hot reload loses them, R:118). Timers: `$.clock.every/after` (T:3426); never `setInterval`.
4. Any plugin may READ any other plugin's `$.state` value; only the owner writes it (T:3381). That is the only cross-plugin channel (`$.store` is per plugin, T:3345). A plugin that reads a peer's atom declares the peer's slice in `shared/peers.d.ts` (copied into its `types/index.d.ts`), treats a missing atom (peer not installed) as "no information", and never depends on it for correctness.
5. State never holds secrets, file contents, command output, prompts or env values. Store derived numbers and short labels only. Checkbox and task labels (<= 60 chars, already model-visible) may sit in `$.state`, never in `$.store`.

## 3. Hook discipline
1. Every hook is `on(...)` followed by `.catch(($, e, next) => next(e))`, except gating hooks (section 3.4).
2. Observers call `next(e)` once, never rewrite `e`, never return without it. Work after `next` is wrapped in try/catch and never delays the result beyond its budget (section 8).
3. `tool.call` hooks ignore tools they do not own and never change a result. The only permitted changes: Protected Files denies; Typecheck Feedback appends `context` (T:12735).
4. Gating hooks (Protected Files, Delegation Guard deny mode) judge BEFORE `next`, are synchronous where possible, and use `.catch(($, e, next) => next.called ? next(e) : decideFromEventOnly(e))` where `decideFromEventOnly` re-runs the pure matcher and denies only on a match (R:79).
5. Subagent events carry `agentId` (`AgentLoop`, T:194). Each spec says whether it counts main only, subagents only, or both.
6. A hook never calls `$.model.*`, `$.prompt.submit` or `$.agent.spawn` unless its spec says so. None of the five plugins spend tokens.
7. (3.1a) A `ui.render` hook (band, pane, any component) makes only `$.state.get`, `$.clock.now` and `$.ui.resolve` calls. Never `$.store`, `$.settings`, `$.agent`, `$.process`, `$.fs`, `$.http` or `$.model`. Each `$` call is a worker hop, and the whole AbovePrompt chain of every plugin is one dispatch, so one slow hook delays every plugin's row (observed live 2026-10-12: a store scan in usage held awareness's row about 3 s and up to 30 s). Work whose cost grows with stored data runs in event hooks or timers and publishes to an atom. A band hook computes its segments after `await next(e)`.

## 4. Band composition (AbovePrompt)
1. Each plugin registers exactly ONE `ui.render{component:'AbovePrompt'}` hook. Pattern from `AP:hooks/register.tsx:368-433`: `inner = await next(e)`; return `inner` when `e.props.hasSurvey` (T:10259), when `e.props.view.agentId` is set (main transcript only, T:10300), when `e.props.maxRows < minBandRows` (option, default 4), or when the plugin has no segment to show. Otherwise `<Box column>{below}{row}</Box>` with `below = inner.type==='engine' ? null : inner`.
2. Inside a plugin, each mod contributes `Segment = { id, order, priority, pinned?, variants: Variant[] } | null` via `segments(ctx)`. `Variant = { px, cells, svg, text, alt }`: `px` desktop width, `cells` terminal width, `svg` an SVG fragment 30 px high at origin 0,0, `text` the terminal string, `alt` the same string as the terminal text without colour.
3. `shared/band.tsx` `composeRow(segments, W, cols)`: drop nulls; start every segment at `variants[0]`; while total px (plus 12 px gaps) exceeds W, move the lowest-priority (largest number) shrinkable segment to its next variant; if none can shrink, drop the lowest-priority non-pinned segment. Display order is `order`, not priority. Returns `{ svg, alt, text }` or null.
   After the shrink/drop loop, `composeRow` runs a grow-back pass (F28): while the total still fits the limit, move the highest-priority (smallest number) segment that has a wider variant to that variant, and re-add dropped segments in `order` when their narrowest variant fits. The final row therefore never leaves room unused that a wider variant would fit in. A variant's `px` is never smaller than the width its `svg` draws (nothing is clipped by its own Svg box). The px fit and the cell fit remain independent.
4. Desktop: one `<Svg source alt width height=30>` per plugin row, `W = clamp(bodyColumns*8 - 16, 180, 1600)` as in `AP:hooks/register.tsx:392`. Buttons that must be pressable (pets button, dismiss) are `Button` elements beside the Svg, not inside it. Terminal: segments' `text` joined with two spaces in a `<Text wrap="truncate-end">`; colour by `color`/`dimColor` only.
5. Plugins coexist by stacking: row order across plugins is load order and not controllable; specs and tests never assert it. A plugin above that draws without `next` hides ours (known, `AP/README.md`). Observed live 2026-10-12: savvy-progress (1.2.0) draws its own AbovePrompt tree without calling `next` once its `progress` tool has run, which hides every Bento row until it is dismissed or the plugin is removed. Steady-state rows: usage 1, dev 1, awareness 1 (only while a turn runs or a timer runs), agents 1 (only while subagents run or review items wait), safety 0 (status text only). Worst case 4 rows; each plugin is silent when `maxRows < minBandRows`.
6. Panes: one pane id per surface of data (`cache-clock`, `delegation`, `pets`, `pr-radar`, `changes`, `ports`, `focus`); `$.ui.open({id,title})` (T:2500); auto-open at most once per session and only if `e.viewport.isFullscreen` or the user ran the command. Never `holdToasts`.
7. `$.ui.status(text)` (T:2477) is used for one-line fallbacks when a plugin has no band (`-p` runs, `hasBand` false). One status per plugin. Any plugin that writes `$.ui.status` as a no-band fallback decides per write from `$.session.surfaces()` and clears its text once when a surface appears.

## 5. Look (desktop SVG)
1. Tokens: the CSS block in `06-still-room-digest.md` ("Still Room tokens for an SVG style") is embedded once per SVG via `tokens.ts`. Dark default, light via `prefers-color-scheme`. Radius 0, bevel recipe (edge 2 px, hi top-left, shade bottom-right, solid drop), segment meters 12 cells 8x10 px gap 2, no gradients, no blur, no spinner. Steps animation only (`steps(3|4)`), wrapped in `prefers-reduced-motion: no-preference`.
2. Fonts: Silkscreen for caps labels and numerals, Space Mono for machine text, Chivo for sentences, each with the fallback stack from the digest; never below 9 px. Write caps in the string (no `text-transform`).
3. Signal colours (ok/warn/danger/arcane) only as segment fills, 2 px edges and glyphs; text uses `--l-*` label colours. Orange `--accent` = the user's thing, blue `--rival` = the other party.
4. Voice: caps `VERB · OBJECT` headlines of at most 4 words; sentence-case detail, dry, digits for numbers; no exclamation marks; errors say what happened plus the one fix.
5. Mascots: `shared/mascots.ts` holds `POM_IDLE` and `CARROT_IDLE` (160x160 PNG, 13 KB and 12 KB, base64 about 18 KB and 17 KB) from `research/brainstorm/assets/`. Drawn as `<image data-mascot="pom|carrot" href="data:image/png;base64,..." width=40 height=40>` inside the SVG (the `data-mascot` attribute is what contract tests assert on; cast rule: Pom = working agents and focus/cache, Carrot = burn, review queue and delegation guard headers). Whether the desktop's Svg scrub keeps `data:` images is UNVERIFIED (T:12272 says it "draws it as an image" and strips scripts only). Probe in the first acceptance run: mount an Svg with a 1-pixel data image and ask the user to look. Fallback when the probe fails (`options.mascots = 'auto'|'on'|'off'`): draw the Still Room block mark (a 14x14 bevelled square in `--accent`, `--rival` for Carrot) in the same box. One SVG source must stay under 131072 characters (T:12272); at most two embedded mascots per SVG.
6. Terminal stills: `Image` with `source:{png}` (T:5315, kitty/Ghostty only), `columns 6, rows 3`, only when `options.terminalStills` is true (default false); otherwise glyphs from section 6.

## 7. Toasts
1. `$.ui.toast(text, {timeoutMs})` has text and a timeout only (T:2447): no buttons, no colour, no surface hint. The mockups' action buttons (SLOW, PING, CHECK) are NOT possible; every toast names its command in the text ("Run /burn.").
2. Format: `TITLE IN CAPS · short detail. Run /cmd.` at most 140 characters, one line.
3. `shared/toast.ts` `createLimiter({minGapMs, quiet})`: `offer(id, text, {priority})` returns `shown | queued | dropped`. Awareness' Heads-Up uses `minGapMs = 60000`. Other plugins use their own limiter (30000 default; `dev` PR Radar uses 60000) and only for the events their spec lists. Safety denial toasts are limited per path (1 per 30 s).
4. The engine also limits: one toast per plugin replaces that plugin's previous one (R:130).
5. **Shared toast convention (decided 2026-10-11, Q18).** The API has no cross-plugin limiter: `$.store` is private to a plugin (T:3345) and a plugin cannot write another's state (T:3381), but any plugin can READ another's `$.state` (T:3381). So the rule is: each plugin that toasts self-limits with its own `createLimiter` AND publishes `lastShownAt` (epoch ms of its last toast) in its own `$.state` atom (`awareness.headsup.lastShownAt`, `dev.toast.lastShownAt`). `createLimiter({minGapMs, peers})` reads the peers' atoms (`awareness.headsup`, `dev.toast`) before `offer`; if any peer showed a toast less than `minGapMs` ago the offer is `queued`, and it also reads `awareness.focus.phase` (`'focus'` = quiet) and `awareness.headsup.mutedUntil` (quiet while in the future). Missing peer atoms = no constraint. Best effort only: two plugins offering in the same tick can both show; this is accepted. The 1-per-minute rule binds Heads-Up (`awareness`) and the PR Radar failing-check toast (`dev`). Safety denial toasts (per-path 30 s) and Delegation Guard (30 s) are out of band on purpose: they report an action just taken.

## 8. Performance and process execution
1. `shared/proc.ts` `run(argv, {cwd, timeoutMs})` wraps `$.process.run` (T:3515): rejects become `{ok:false, reason}`, default timeout 10 s, never throws. **CONFIRMED (live probe 2026-10-11):** `$.process.run` works in a Claude desktop-app session (a probe mod ran `git --version` from a `tool.call` hook and got exitCode 0); the types doc says "CLI only" (T:3493) but the desktop Code tab runs the CLI engine. So process-based mods are the expected path on both hosts. Defensive code only: `proc.ts` still runs a cheap capability probe once per session (`git --version`); if it ever rejects (a future host, a sandbox) the plugin marks process-based mods `unavailable (needs host commands)`, shows that once in its status text, and does nothing else. Tests cover this path with a mocked rejection; it is not the normal case.
2. Circuit breaker per command family: 3 consecutive failures -> pause 5 min, then 15 min, cap 60 min; reset on success. Never run two instances of the same family at once; a running family drops new requests.
3. Polling floors: git local queries >= 5 s apart and event-driven; `gh` >= 60 s; `lsof` >= 15 s. Nothing polls when the last user input is older than `idleMinutes` (default 30) except timers the user started.
4. Only one 1 s tick per plugin, running only while a visible countdown exists (section 4 of each spec says which). Adaptive: 1 s when a countdown is under 120 s, 5 s under 10 min, else 30 s.
5. Hook budget: work added to `tool.call` after `next` is capped at 300 ms unless the spec gives a larger bound (Typecheck Feedback). Anything slower goes to a background timer and a state atom.

## 9. Privacy
No secret values in state, store, toasts, logs or deny messages. Show paths and counts, never contents. `gh` and git output is parsed and discarded; only derived fields persist. Checkpoint refs live in the local repo only. `$.ui.log` is used for errors, with `{to:'debug'}` for diagnostics.

## 10. Tests and acceptance (all plugins)
1. Behaviour contracts in each spec are the only input of the code-blind tester. Tests live in a separate repo `bento-mods-tests/<plugin>/*.test.ts` and are copied into a temp copy of the plugin by `scripts/run-contract.sh <plugin>`, which runs `claude plugin test <tmp>` and prints pass/fail counts and failing test names only. Builders never read the tests.
2. Contract statements assert on: `textOf(tree)` (labels, text, Svg `alt`), toast texts captured from `ui.toast`, `{deny}` strings, command `text`, and `$.state`/`$.store` values named in the spec. Every UI statement runs on `terminal` and `desktop` and the two texts must be equal (alt == terminal text).
3. Time is mocked (`mock.clock`), model usage is injected through `turn.step` results, process output through a mocked `process.run` hook.
4. Gate for every plugin: `claude plugin validate plugins/<name>` clean; `tsc -p plugins/<name>` clean (tsconfig in T header); `claude plugin test` green; the manual list in its spec.
5. Mocked-process tests prove parsing. Real-process behaviour (git, gh, lsof, tsc) is checked once by hand on this Mac (the manual list).

## 12. Option key spelling (added 2026-10-12, build finding)
`claude plugin validate` rejects dots in `userConfig` keys ("Invalid key in record"). Canonical key = the spec's dotted name with every `.` replaced by `_` (e.g. `mod.git.enabled` -> `mod_git_enabled`, `tc.mode` -> `tc_mode`). Manifests and contract tests use the underscore form; code may also accept the dotted form.
`claude plugin validate` follows `$` only inside `register.tsx`, not across imports: pass mods a facade built in register.tsx (see plugins/dev `mkD`) and declare atoms there.
Further validate rules found during build (2026-10-12): `on` cannot be passed to a non-local function (so `mod.register(on, ctx)` from s1.2 fails; mods become pure helpers or sections of register.tsx); only one unmatched hook per event per plugin (use a matcher such as `{}` for extra ones, runtime match UNVERIFIED); `types/index.d.ts` must be import-free (copy peer slices in). Host: `$.prompt.submit` and `$.session.compact` are refused from `command.run`; defer with `$.clock.after(0)` (live acceptance UNVERIFIED).
Test-harness rule (2026-10-12, from the safety referee): test mocks stand for the engine. Bottom hooks for noun calls answer `{ value: <result> }` (`session.cwd/id/surfaces`, `ui.toast/status`, `fs.*`, `process.run`, `store.*`, `command.list` -> `{value: []}`, `command.register` -> `{value: undefined}`); lifecycle events (`session.start` -> `{cwd}`, `command.run` -> `{}`/`{text}`, `turn.complete` -> `{text:''}`, `session.end` -> `{}`) return their direct result. A hook returning anything else is skipped and the plugin sees "no implementation for <event>".
More harness rules (2026-10-12, compact referee): `mock.clock` holds `$.clock.after(0)` until `clock.settle()`/`advance`; raise `prompt.compose` with a full `PromptComposeInput` (incl. `promptModel`); register beneath-hooks before the test's first `$` call (one world per test).
Mascot probe (s5.5) CONFIRMED 2026-10-12: the user saw the Pom still (data: PNG inside <Svg>) above the prompt in the desktop app. `options.mascots` default stays 'auto' = stills on desktop; block-mark fallback only if a future host strips images. Probe mod deleted.
More harness rules (dev referee): `state.get` answers `{ value: { value, version } }`; a test's `$` has no `state` noun (observe `state.set`); `$.tool.call` results omit `isReadOnly`.
